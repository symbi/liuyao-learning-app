# MVP 实施计划

## 目标

做出一个能在本地浏览器运行的最小网页：输入六次摇卦结果，展示本卦、动爻、变卦和逐步计算说明。

## 阶段 0：准备与核对

- [ ] 阅读本仓库的项目背景和规则状态文档。
- [ ] 找到用户本地现有笔记、术语表、案例和第三课整理资料。
- [ ] 核对首版需要的硬币计数映射与六次输入顺序。
- [ ] 至少选出一个经课程资料或用户确认的标准案例作为测试。
- [ ] 不把未经核实的规则写进正式计算逻辑。

## 阶段 1：最小网页

- [ ] 设计六行输入界面，每行代表一爻，并标明初爻至上爻。
- [ ] 每次摇卦可记录三枚硬币的原始结果，或经过核实的花面数量。
- [ ] 输入校验：必须有六次有效记录；错误要给出可理解的提示。
- [ ] 显示每爻的原始输入、阴阳结果、动静状态。
- [ ] 显示本卦和变卦的六爻结构。
- [ ] 展示逐步计算明细，方便人工复核。

## 阶段 2：规则数据化与测试

- [ ] 将计算规则与 UI 分开存放。
- [ ] 每条规则包含 ID、描述、输入、输出、状态、来源和备注。
- [ ] 为常规爻、动爻、变爻和输入顺序编写单元测试。
- [ ] 使用已人工核对的案例做端到端测试。
- [ ] 对缺少依据的规则明确报出“待核实”，不要用猜测结果冒充正确结果。

## 阶段 3：扩展排盘

按课程资料核实的优先顺序逐项实现：

- [ ] 纳甲
- [ ] 六亲
- [ ] 世应
- [ ] 旬空
- [ ] 六冲、六合
- [ ] 日辰、月建等课程涉及的项目
- [ ] 案例练习与自测

每项功能开始前，先补齐来源、规则说明与测试案例，再实现界面。

## 建议的技术路线

首版优先采用轻量的前端网页，不急着引入后端或数据库。具体框架可由开发工具先检查当前仓库，再选择维护简单、容易在不同电脑运行的方案。避免在需求和规则尚未核实前引入不必要的基础设施。

## 验收标准

1. 用户能清楚地输入六次结果，并确认每次对应哪一爻。
2. 本卦、动爻、变卦的展示与规则计算一致。
3. 页面能解释每一步用了什么规则。
4. 自动化测试覆盖核心规则，标准案例结果可重复。
5. 未核实的规则不会被伪装成已确认的结论。
6. 在另一台电脑克隆仓库后，按 README 指引即可启动。
