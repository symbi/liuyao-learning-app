# 多体系易学知识大脑：长期架构方向

> 文档类型：长期架构愿景与后续规划（非当前里程碑实施任务）
> 版本：0.1
> 规划日期：2026-11-24
> 状态：方向已确认；具体数据模型、处理流程和实施顺序待后续试点验证
>
> **重要边界：** 本文记录未来知识体系扩展方向，不改变当前 Phase 1 的执行顺序，不构成 M3–M8 或云端资源创建的实施授权。当前 Phase 1 仍以现有六爻课程、课堂案例完成云端在线分析闭环为第一目标，见 [Phase 1 实施计划](phase1-implementation-plan.md)。

## 1. 愿景

建设一个统一的、可持续扩展的“易学知识大脑”：能够收录不同易学体系的书籍、课程、注释和案例，对古文及理论进行有出处的理解与整理，再根据用户当前的问题选择正确的知识体系进行检索和回答。

整体原则：

**底层统一，知识分域，应用按体系取用。**

这不是把八字、六爻、易经等内容混成一个没有边界的文本库。它们可以共用底层存储、来源管理、向量检索和在线服务，但知识对象必须保留所属体系、适用范围、来源身份和证据状态。

第一阶段优先服务六爻应用；八字、易经和其他领域先作为独立知识空间保存，不因此改变六爻产品的核心判断规则。

## 2. 知识空间划分

初步规划四个逻辑知识空间，并允许未来扩展：

| 知识空间 | 典型内容 | 在六爻分析中的默认用途 |
|---|---|---|
| `liuyao`（六爻） | 六爻专著、纳甲、世应、六亲、六神、动变、旬空、课程和课堂案例 | 主要依据，优先检索 |
| `bazi`（八字） | 《滴天髓》《子平真诠》等子平命理书籍、十神、格局、月令、岁运 | 默认隔离，不作为六爻断卦依据 |
| `yijing`（易经） | 《周易》经文、卦辞、爻辞、象传及不同注本 | 按具体问题选择性引用，不自动等同于六爻技法 |
| `common`（通用基础） | 阴阳、五行、天干地支等跨体系基础概念 | 可作为辅助知识，但须检查具体语境和定义 |

未来可增加风水、择日等知识空间，但不得因为增加新领域而改变既有领域的语义和规则。

### 2.1 体系归属与适用范围是两件事

每个知识对象至少应区分：

- **所属体系（discipline）：** 这条知识源自哪个体系，例如六爻、八字、易经或通用基础。
- **适用范围（applicability）：** 它能用于什么任务，例如直接作为六爻依据、通用基础参考、跨体系比较，或不适用于当前六爻判断。
- **来源角色（source_role）：** 主要依据、辅助参考、背景材料或比较材料。
- **证据状态（evidence_status）：** AI 草稿、待核对、已核对、存在争议等。

书籍的所属体系不应只凭书名自动决定；应结合书籍内容、版本、章节和具体段落进行分类。一本书中也可能包含不同层次的材料，必要时允许段落级分类。

## 3. 三层处理架构

### 第一层：Source Collector——原始资料采集

由现有独立项目 `symbi/liuyao-source-collector` 负责。

职责：

1. 发现并检查用户指定的书籍、网站或文件。
2. 按允许的范围采集章节和正文，尽可能保留原始文本。
3. 保存书名、作者/题署、版本、章节层级、原始 URL、采集时间、内容哈希和原始定位。
4. 记录每本书、每个来源的版权与许可状态，以及是否允许本地保存、私有仓库存储、云端 AI 处理和再分发。
5. 输出版本化的 **Raw Reference Package**，作为原始资料交接格式。

边界：

- Collector 的首要职责是忠实采集和保存来源，不负责改写或解释原文。
- 原文、不同版本、注释和后续生成的解释必须可以区分。
- 采集一项资料的许可不自动代表允许将全文发送给 ChatGPT、Gemini 或其他第三方云端模型。
- 当前 Collector 已有自己的采集和 Package 规范；本计划不要求把知识解释逻辑直接塞进现有采集流程，也不要求现在修改 Collector。

### 第二层：Knowledge Processing——古籍理解与知识整理

这是目前尚未建立为独立自动化系统的逻辑层。初期可以由 ChatGPT 网页进行人工辅助处理；后续再把稳定、重复的步骤实现为脚本或独立处理组件。

输入：第一层生成的 Raw Reference Package。

处理内容：

1. **文本结构理解：** 按书、篇、章、段落及注释结构组织文本，保留原始段落定位；不能只按固定字符长度切割而破坏语义。
2. **文本辅助理解：** 对文言文提供现代汉语解释、必要的逐句释义和术语说明，同时保留原文。
3. **概念整理：** 识别术语、概念定义、同名异义、别名和概念之间的关系。
4. **理论整理：** 归纳原文表达的理论主张、推理链、成立条件、适用范围、例外和限制。
5. **命例整理：** 提取书中案例/命例、已知条件、作者或注家的判断过程和结论；不能把案例结论脱离原始条件。
6. **注释与版本比较：** 区分原文、古代注家、现代注释、译文和 AI 综合解释；记录不同版本或注家的异同、冲突与不确定性。
7. **体系分类：** 标记所属知识空间、适用范围、来源角色；发现跨体系相似概念时，先建立“比较/关联”，不能直接认定为同一概念。
8. **质量控制：** 每条解释和理论主张必须回链到原始书籍、版本、章节和段落；记录模型、处理时间、处理规则/Prompt 版本及人工核对状态。

输出：版本化的 **Knowledge Package**。它是从原始资料派生出的结构化解释与知识对象，不替代、不覆盖 Raw Reference Package。

重要规则：

- AI 翻译、总结、概念抽取和理论归纳一律先视为候选结果，不自动成为已确认知识。
- 每个候选知识对象都必须保留原文证据、定位、来源版本和生成记录。
- 人工核对后可以标记为已核对；存在不同解释时保留并列观点及各自出处，不强行合并。
- 如果脚本无法可靠理解古文、术语或上下文，应输出待核对/不确定状态，而不是编造完整解释。
- 只有来源许可明确允许云端处理时，才可以把对应全文或片段发送给云端 AI；否则只能按获准方式处理，或等待用户确认权限。
- 当前 Collector README 将首本《基础知识》（`3_1`）的 `allow_cloud_processing` 标记为 `false`；在取得适用的明确许可前，不得把该书全文提交给 ChatGPT、Gemini 或其他云端 AI 做知识整理。其他书籍也必须逐本检查，不能沿用某一本书的权限。

**组件位置暂不冻结：** 第二层先通过 ChatGPT 辅助流程验证 Knowledge Package 格式。后续自动化时，可以做成独立脚本/服务/模块；是否新建第三个 Repository，留待试点后决定。为保持职责清晰，不默认把它并入 Collector 的采集主流程。

### 第三层：Learning App——统一知识底座与按需应用

由 `symbi/liuyao-learning-app` 负责。

长期职责：

1. 验证 Raw Reference Package / Knowledge Package 的结构、版本、来源身份、许可信息和定位。
2. 将获准的原文、注释、解释、概念、理论、条件和案例导入统一知识底座。
3. 使用 Neo4j 管理文档、版本、段落、概念、理论主张、案例、来源证据及跨体系关系；Embedding 和检索服务作为共享基础设施。
4. 保留体系隔离、来源可信度、适用范围和证据状态，供检索阶段执行过滤和排序。
5. 由在线分析服务根据用户任务选择一个或多个知识空间，构建有出处的上下文，再调用生成模型回答。
6. 最终输出必须区分原文、注家解释、人工整理、AI 综合解释和模型推断，并提供可回查的来源定位。

统一底层不等于所有知识必须使用同一套规则、同一索引或不加区分地一起检索。具体 Neo4j 标签、属性、索引和检索实现待设计阶段确定。

## 4. 跨体系隔离与引用规则

### 4.1 六爻分析的默认检索策略

当用户请求六爻排卦或断卦时，默认策略：

1. 优先检索 `liuyao`：六爻课程、已核对规则、六爻书籍和老师课堂案例。
2. 在问题需要时检索 `common`：例如阴阳、五行、天干地支等基础知识；引用时仍须检查六爻语境。
3. 只有问题涉及《周易》经文、卦辞、爻辞或象义时，才有选择地检索 `yijing`。
4. 默认不检索 `bazi` 作为六爻判断依据。只有用户明确要求八字与六爻比较，或明确允许跨体系研究时，才加入相关八字材料。

八字资料可以成为大脑的一部分，但不能因为也有五行、干支或“六亲”等相似术语，就自动参与六爻断卦。

### 4.2 相似术语不自动等同

跨体系概念必须保留体系限定。举例：

- 八字中的十神与六爻中的六亲不能因为都表达关系分类，就直接建成同一个概念。
- 同名术语在不同书籍、注家或体系中可能定义不同。
- 跨体系关系优先使用“相关”“对照”“类比”“存在差异”等显式关系；未经论证，不建立等价/同义关系。
- 跨体系材料用于回答时必须明确标注“比较参考”，不能伪装成当前体系的权威规则。

### 4.3 检索与生成的双重防线

不能只依赖生成模型“记得”哪些材料不该使用。应用层应先按用户任务选择检索范围，再把允许的知识空间、来源角色和禁止越界规则写入生成上下文。生成后还应检查引用是否来自允许的体系，跨体系引用是否有明确理由和标签。

## 5. 建议的 Knowledge Package 内容（概念草案）

最终 Schema 尚未冻结。当前可以先按以下概念准备：

| 对象 | 关键内容 |
|---|---|
| Book / Edition | 书名、作者/题署、版本、语言、知识体系、版权/处理许可 |
| Passage | 稳定段落 ID、原文、章节层级、页码/段落定位、内容哈希 |
| Commentary | 注家/译者、对应 Passage、注释原文、版本定位 |
| Explanation | 白话解释、逐句释义、解释者/模型、生成时间、核对状态 |
| Term / Concept | 术语、定义、所属体系、同义词/异名、出处 |
| Theory Claim | 理论主张、推理依据、成立条件、适用范围、例外、反例 |
| Case / Example | 原始条件、作者/注家分析、结论、对应原文段落 |
| Cross-system Relation | 两个体系中概念的关联/类比/差异及论据 |
| Provenance | 原始来源 ID、版本、URL、章节、段落、Hash、许可状态 |

以上只用于明确知识内容的形态，不是本次冻结的 Neo4j Schema。段落、概念、解释和理论之间应保留可回查关系；原始原文不得被 AI 解释覆盖。

## 6. 示例：处理《滴天髓》

《滴天髓》可作为 `bazi` 知识空间中的候选书籍。处理时应：

1. 在 Collector 侧逐本核实采集、私有保存、云端处理和再分发许可。
2. 保留所采集的原文、版本和章节定位。
3. 在 Knowledge Processing 阶段区分原文、注家注释、现代白话解释和 AI 综合理解。
4. 对旺衰、气势、五行等概念提取定义、上下文、理论条件和例子，并保留对应段落出处。
5. 标记为 `discipline=bazi`；适用范围按实际内容确定，不能把整本书不加区分地标成六爻规则。
6. 将来六爻分析需要通用五行基础知识时，只能引用经过适用性判断的通用基础对象；《滴天髓》的八字专属判断仍留在八字空间。

这只是长期处理样例，不代表《滴天髓》当前已经采集、获得云端处理许可或完成知识整理。

## 7. 实施阶段建议

本方向按渐进方式建设，不与当前 Phase 1 主路径竞争资源：

- **阶段 A：格式试点。** 选取一部已确认允许相应处理的书籍或一小段获准文本，用 ChatGPT 人工辅助整理，验证原文定位、注释区分、术语和理论对象、核对状态及 Knowledge Package 格式。
- **阶段 B：处理流程固化。** 根据试点经验定义可重复的步骤、提示模板、输出校验和版本机制；先保留人工审查。
- **阶段 C：脚本化。** 对稳定、重复、可验证的工作开发 Knowledge Processing 脚本；复杂解释仍保留人工复核，不追求全自动“理解”。
- **阶段 D：知识库接入。** Learning App 增加 Knowledge Package 的接收、验证、导入和按体系检索能力，按独立任务设计和验收。

当前优先事项仍是 Phase 1 云端主路径 M3 → M4 → M5 → M7 → M8；M6 外部参考资料仍按既定计划延期、不取消。多体系古籍理解与知识处理属于后续扩展方向，不要求现在变更 M3–M8 的范围或顺序。

## 8. 已确认决定与待确认事项

### 已确认的方向

- 建设一个统一的易学知识大脑，底层共享基础设施。
- 六爻、八字、易经、通用基础知识采用独立的逻辑知识空间。
- 六爻是当前产品的主要应用空间；八字默认不能作为六爻断卦依据。
- 通用基础知识可以被不同领域引用，但必须保留语境和适用范围。
- 跨体系比较必须显式、可追溯，不能把相似术语直接等同。
- 采集、知识理解与知识库存储/应用分成三个逻辑层。
- 第二层初期允许 ChatGPT 辅助；尚不决定新建第三个 Repository。
- 原文与 AI 派生知识分开保存，AI 输出必须保留出处和核对状态。

### 尚待试点确定

- Knowledge Package 的正式 JSON/Markdown Schema。
- 书籍、版本、注家、段落、概念和理论对象的最终数据模型。
- 第二层自动化脚本的具体位置、Repository 归属和运行环境。
- 古文翻译、术语抽取、理论归纳的模型和质量评估方法。
- 人工复核的粒度、权限及正式知识晋升流程。
- Neo4j 中的逻辑分域、向量索引分区和检索路由实现。
- 各书籍具体的版权状态与云端处理权限。

---

**本计划的目的，是先把长期方向写清楚，避免未来采集八字、六爻、易经等书籍时把知识混在一起。它不是当前 M3–M8 的实施任务书，也不意味着任何一本书已经获得采集或云端 AI 处理许可。**
