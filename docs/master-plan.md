# 六爻起卦与排盘网页：项目主计划 v1

> 本文是给 Claude Code 的项目入口与实施约定。它描述项目方向、阶段、验收标准和第一项任务；不是已确认的六爻规则教材。规则状态以 `docs/rules-status.md` 为准。

## 1. 产品目标

制作一个轻量、桌面优先、手机也能使用的静态网页，让用户在起卦时可靠地看到：

1. 起卦日期和时间；
2. 该日期对应的年柱、月柱、日柱干支；
3. 六爻起卦输入/记录、阴阳与动静、本卦和变卦；
4. 可复制、可回查的结构化结果，以便用户自行纳甲或交给另一个 AI 对话进行学习讨论。

**第一优先级是历法信息正确、能说明口径并可回归测试，不是复杂动画或 AI 断卦。**

## 2. 仓库分工与安全边界

- Public 应用仓库：`https://github.com/symbi/liuyao-learning-app`。只放应用代码、自写文档、规则摘要、可公开的案例、来源链接及许可证允许公开的材料。
- Private 原始资料仓库：`https://github.com/symbi/liuyao-learning-raw`。保存原始录音转录、未经整理的课次资料和待分类文件。
- 已有项目文档必须先读再改：`README.md`、`docs/project-background.md`、`docs/mvp-plan.md`、`docs/rules-status.md`、`materials/README.md`、`docs/references/`、`docs/lessons/`、`docs/rules/`。
- 不要重复创造第二份规则状态表；新发现写回现有登记文件或补充有明确用途的文档。
- Public 仓库的内容对任何人可见。不得提交课程完整转录、未授权的 PDF/扫描书、秘密、访问令牌、个人资料或公司的资料。现代注释、翻译、校勘本可能有独立版权，即使古籍原作已进入公有领域也不能一概复制。
- 不要把 Private raw 仓库内容自动复制到 Public；每次整理都要检查权利与公开必要性。

## 3. 目标用户流程

1. 打开网页，默认展示当前日期和时间，时区明确显示为 Asia/Tokyo；允许用户选择历史起卦时间。
2. 查看年柱、月柱、日柱；额外明确显示「月建」与「日辰」，不让用户只看到一个含义模糊的“月份/日期”。
3. 用模拟三枚钱逐次记录六次结果，或手动录入真实铜钱结果。每次结果保留三枚钱的原始面值。
4. 按规则得到各爻阴阳、动静、本卦和变卦；输入顺序与最终排盘显示顺序都要明确。
5. 检查结果，复制结构化文本；后续可选择本地保存/导出 JSON。
6. MVP 不调用 AI API、不需要账号、不需要后端、不要求自动判断卦意或自动判分。

## 4. MVP 范围

### MVP A：先做出可靠的设计与历法验证

- 页面布局草图/可预览 mockup。
- 历法库可行性测试与口径说明。
- 日期时间输入、时区显示、年/月/日干支显示。
- 测试数据、错误状态和“不确定口径”提示。
- 如果历法方案尚未通过边界测试，不得把它包装成已验证完成。

### MVP B：可用的起卦页面

- 六次起卦输入或录入；逐次保留三枚钱结果。
- 硬币计数映射必须先从课程资料/用户确认中核实。当前规则状态表中的 COIN-001、ORDER-001、HEX-001 仍待核实，不得自行硬编码成权威规则。
- 显示初爻至上爻的编号和阴阳/动静，并正确生成本卦、动爻、变卦。
- 可复制结构化文本，至少包括起卦时间、时区、年/月/日干支、月建、日辰、六次原始输入、六爻结果、本卦/变卦。
- 基础可访问性、桌面与手机响应式布局。

### 后续阶段（不是 MVP 阻塞项）

- 按课程核实顺序扩展纳甲、六亲、世应、六神、伏神、旬空及其他盘面字段。
- 本地历史记录、标签、JSON 导入导出。
- 课程知识索引、来源定位和案例练习。
- AI 解读只有在用户另行明确要求时再评估；不能默认接入收费 API。

## 5. 页面信息架构 / 初步 UI 要求

采用单页应用，不做原生 APP，不做 Chrome 插件。

1. **页头**：项目名称「六爻起卦与排盘」、简短状态/说明。
2. **起卦时间与历法卡片**：当前时间、选择日期/时间、时区；年柱、月柱、日柱分栏；独立突出「月建：某支」「日辰：某支」；可附农历日期和节气作为核对辅助，但不能用农历月替代月建。
3. **起卦输入区**：三个铜钱及每次投掷结果；支持重新投掷/撤销单次/手动录入真实硬币；六次记录都可见。
4. **六爻结果区**：展示初爻到上爻的输入对应关系；传统卦象通常自下向上画，要避免视觉顺序与输入顺序混淆；动爻显著但不过度装饰。
5. **结果与复制区**：本卦、变卦、动爻、结构化文本复制；错误和未核实规则要明确提示。
6. **说明区**：展示本次使用的历法口径、规则 ID 和来源状态；不输出无依据的断语。

视觉方向：简洁、清晰、像工具而不是营销页面；先追求可读性与可验证性。请先生成桌面版和窄屏版 mockup，再写业务逻辑。

## 6. 技术路线原则

- 先检查仓库现状与现有文档，再选择最简单的维护方案。若仓库尚无实际应用代码，可优先评估 Vite + React + TypeScript。
- 候选历法库见 `docs/calendar-engine-plan.md`。通过适用性、时区与边界测试后再决定是否采用。
- 把 UI 与历法、硬币规则、卦象计算分开；历法使用 adapter/interface，避免 UI 直接依赖第三方库的细节。
- 运行时默认不访问远程日历网站；核心日期计算应能离线运行。在线万年历用于开发阶段交叉核对，不是每次起卦的运行依赖。
- 核心规则放在独立的纯函数/规则模块中，并有自动测试。
- 浏览器本地保存是可选项；若实现，应明确说明清理浏览器数据可能删除记录，并提供导出方式。
- 每次新增依赖要记录理由、版本与许可证；不复制外部项目大段代码。

## 7. 知识与参考资料的使用流程

按 `docs/reference-research-plan.md` 执行：

1. 先盘点现有资料和已有外部来源记录，不重复整理。
2. 为来源记录名称、URL、许可证/版权状态、可用内容、最后核查日期、与本项目的关系。
3. 将每条规则标成「课程明确」「外部参考」「推断」「有分歧」之一，并记录原始文件路径及页码/时间戳（若已知）。
4. 未确认来源或有争议的算法只登记为待核实，不进入正式计算。
5. 以有明确 API、测试和许可证的开源代码作为交叉核验参考；不要仅凭星数或 README 的自我描述认定正确。

## 8. 开发阶段与交付物

### Phase 0 — 只做规划和原型
- 阅读现有项目全部核心文档并检查目录。
- 产出可预览的 `docs/ui-mockup.html` 或 `docs/ui-wireframe.svg`（桌面+手机）及 `docs/architecture.md`。
- 产出历法方案决策/测试建议；列出硬币映射、六次顺序、年/月/日切换口径等所有未决项。
- 暂时不要引入大量依赖，不要直接实现整套纳甲或 AI 解读。

### Phase 1 — 历法引擎 proof of concept
- 写一个仅用于验证的 adapter/演示或最小模块，打印已知日期的年柱、月柱、日柱、月建、日辰和节气。
- 建立可重复的测试夹具；覆盖节气换月、年界、日界、时区及历史日期输入。
- 把选择的口径、库版本、来源、已知限制记录下来。
- 只有所有关键测试通过或明确列出尚未解决的风险后，才能进入下一阶段。

### Phase 2 — 起卦与基本卦象
- 实现已确认的硬币输入映射、六爻顺序、本卦/变卦。
- 为每个边界情况补单元测试，用课程案例作为端到端测试。
- 暂不接 AI API。

### Phase 3 — 页面整合与用户验收
- 完成响应式页面、复制、清晰错误提示。
- 通过下述验收清单。
- 更新 README 启动说明与维护者说明。

### Phase 4 — 扩展装卦与知识库
- 每次只实现一个已核实的规则主题；先登记来源、写规则、准备案例和测试，再写代码。
- 以独立模块逐步实现纳甲、六亲、世应等；不因“想展示完整盘面”而猜规则。

## 9. MVP 验收标准

- [ ] 用户能看见当前或所选起卦时间和明确的时区。
- [ ] 页面明确展示年柱、月柱、日柱，以及独立的月建、日辰。
- [ ] 日期以指定时区解释，不能因 UTC 转换而意外前后移动一天。
- [ ] 年界、节气换月、子时/日界的采用口径在文档里写明；若课程规则未确认，显示为待确认而非静默决定。
- [ ] 有包括 2026-10-28 的人工交叉核对案例，参考值为丙午年、戊戌月、乙亥日；该样例是外部参考锚点，最终仍需按项目确定的历法口径验收。
- [ ] 六次原始硬币输入与六爻位置可追溯。
- [ ] 未确认的 COIN-001/ORDER-001/HEX-001 不能被当作已确认规则。
- [ ] 本卦与变卦的核心计算有自动测试。
- [ ] 页面能复制结构化结果，文本中的行序和时间信息明确。
- [ ] 克隆仓库后，按 README 可以启动；测试命令可重复运行。
- [ ] 无 API key、无必需后端、无必需的运行时日历网络请求。
- [ ] 没有把私人课件/原始转录或无授权古籍版本提交到 Public 仓库。

## 10. 给 Claude Code 的第一条任务

请先不要立即实现完整网页。先阅读仓库 README、项目背景、MVP 计划、规则状态、现有课程笔记、外部参考文档和规则文件；检查仓库当前代码与依赖。然后：

1. 对照本文和 `docs/calendar-engine-plan.md`，给出一页以内的执行摘要、发现的现有工作、风险/未决问题。
2. 创建 `docs/ui-mockup.html`（优先，可浏览器打开）或 `docs/ui-wireframe.svg`，包含桌面和手机布局。图中必须展示年柱/月柱/日柱、月建/日辰、起卦时间/时区、六次硬币记录、六爻结果、本卦/变卦及复制操作。
3. 创建或更新 `docs/architecture.md`，用 Mermaid 画出模块关系：UI → calendar adapter → deterministic calendar library；UI → coin rules → hexagram logic；rules/source registry → test fixtures。
4. 创建待决策清单，特别标出历法换界口径和硬币计数映射。不得自行把待核实项目改成已确认。
5. 先报告设计图与决策清单，**暂停在这个规划里程碑，等待用户检查后再大规模写功能代码**。如果仓库实际状态与本计划不一致，先说明差异并调整计划，不要覆盖已有工作。
