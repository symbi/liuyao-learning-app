# 历法引擎方案与验证计划

## 1. 为什么把历法放在第一位

本应用至少需要正确显示起卦时间对应的年柱、月柱、日柱，并明确呈现六爻语境中的「月建」和「日辰」。如果历法输入错误，后续卦盘即使画得漂亮也没有意义。

不应把「调用一个日历库」等同于「历法规则已验证」。库的能力、库使用的换界口径、时区/日期转换与课程采用的做法，都必须分别检查。

## 2. 建议的数据契约

建议应用自己的类型与第三方库无关，结构大致如下（字段可依据库 API 调整）：

```ts
type CalendarConventionStatus = "confirmed" | "provisional" | "disputed";

interface CastDateContext {
  instantISO?: string;
  localDateTime: string;       // 用户可读的当地年月日时分
  timeZone: string;            // IANA timezone，例如 Asia/Tokyo
  gregorianDate: string;       // YYYY-MM-DD
  lunarDateText?: string;      // 可选辅助显示
  yearPillar: string;          // 例如 丙午
  monthPillar: string;         // 例如 戊戌
  dayPillar: string;           // 例如 乙亥
  monthBuilder: string;        // 月建地支，例如 戌
  dayBranch: string;           // 日辰地支，例如 亥
  currentSolarTerm?: string;
  previousSolarTerm?: string;
  nextSolarTerm?: string;
  conventionId: string;
  conventionStatus: CalendarConventionStatus;
  sourceLibrary: string;
  sourceLibraryVersion: string;
}
```

初版可以只显示年柱、月柱、日柱、月建、日辰、起卦时间和时区。农历日期/节气作为辅助诊断信息。时柱不是当前 MVP 必需项；只有课程确实需要且口径明确后才加入。

## 3. 候选实现

### 候选 A：`6tail/lunar-typescript`

- 项目：<https://github.com/6tail/lunar-typescript>
- README 声明支持公历、农历、儒略日、干支和节气，并声明 MIT license。
- 使用 TypeScript/JavaScript 对静态前端比较方便；无需运行自己的后端。
- 采用前必须检查当前 release、API 文档、边界测试与时区注意事项；把版本锁定在 lockfile。
- 不要直接在 UI 组件中到处调用库 API。建立 `calendarAdapter`，将依赖集中在一处。

### 候选 B：`6tail/lunar-javascript`

- 项目：<https://github.com/6tail/lunar-javascript>
- 同一项目生态的 JavaScript 版本，可作为 API/实现对照；不需要同时把两套库都打包进正式应用。
- README/package metadata 声明 MIT license；正式使用前仍检查发布版本和许可证文件。

### 参考引擎（不作为前端直接依赖）

- <https://github.com/yaomancy/liuyao-engine>：Apache-2.0 的 Python 六爻引擎，公开说明包含四柱、装卦和测试/交叉验证思路。可用来建立测试问题和理解数据契约；由于它是 Python 项目，除非明确决定做后端，否则不要把它引入纯静态网页运行链。
- 可再对比 `sxtwl` / `lunar-python` 等独立历法实现，作为开发阶段的交叉检查来源，而不是把所有库一起加入产品 bundle。

## 4. 必须明确的历法口径

在核对课程和库行为之前，下列规则均应作为待决策项记录，不能只靠默认值：

1. **年柱换界**：按立春还是农历新年切换？不同排盘规则可能采用不同边界。记录课程依据及测试。
2. **月柱/月建换界**：六爻月建应重点核对节气「节」的换月边界，而不是把农历月份直接当作月建。当前月柱算法与月建地支应互相一致并可解释。
3. **日柱换界**：公历日期的本地午夜与子初（约 23:00）换日可能存在不同口径。要记录用户/课程采用的约定；不能默默改变用户选定的日期。
4. **时区**：默认显示和计算时区为 `Asia/Tokyo`，并让用户知道页面正在使用哪个时区。历史日期/时间输入必须保持当地日期，不应因为将日期字符串当 UTC 时间再转换而错一天。
5. **交节瞬间**：如果用户选择的时间恰好接近节气交接点，必须按库提供的精确时刻和选定时区处理；若精度/口径不能确认，应显示“需人工核验”。
6. **显示字段**：年柱/月柱/日柱是整柱；月建是月支，日辰是日支。UI 不要把它们混称为“月份”“日期”。

## 5. 起始交叉核对锚点

以公历 2026-10-28 为第一条 fixture。两个线上万年历查询参考到以下结果：

- 年柱：丙午
- 月柱：戊戌
- 日柱：乙亥
- 月建：戌（从月柱的月支显示）
- 日辰：亥（从日柱的日支显示）
- 当日节气范围：霜降后、立冬前

来源：
- <https://www.rili.com.cn/wannianli/2026/1028.html>
- <https://www.qqsoon.com/jin-ri-tian-gan-di-zhi/>

此 fixture 是外部交叉检查锚点，不可替代课程口径确认。应在测试文件注释里写明来源、日期、核查日期与状态。如果第三方库结果与网站不一致，先调查口径、时区、交节时刻和数据版本，不能简单选择“看起来更像”的那个。

## 6. 测试矩阵

最少准备以下类别的 fixtures，并保存预期值和来源：

- 普通日期：例如 2026-10-28。
- 立春附近：边界前、边界瞬间/后（用于验证年柱口径）。
- 寒露、立冬等节气附近：换月前与换月后；选择课程规则指定的「节」边界。
- 春节附近：用于判断库的农历新年与年柱切换是否混淆。
- 每月不同干支：覆盖月干支推导规律，不能只测试一个月份。
- 日柱连续性：至少连续多日，确保相邻日期的干支连续变化。
- 当地 22:59、23:00、00:00、00:01：验证子初换日或午夜换日设置。
- 不同时间区间（至少 Asia/Tokyo 与 UTC 的同一瞬间）：确保显示时区与实际日柱计算一致。
- 历史日期、闰年 2 月 29 日。
- 用户手动选择日期与默认“现在”输入：不得无意修改用户的选定日期。

不要凭空编造边界的预期值。交节瞬间和换界预期应由已验证的库结果与独立来源确定，并把该预期的依据记录下来。

## 7. 运行时架构与错误处理

- 计算必须在本地运行，不需要每次打开网页都访问某个万年历网站。
- 在线网站只用于开发期间交叉验证；网页无法连接外网时，日柱等核心结果仍应可计算。
- 将第三方库封装在 adapter 内；业务代码只依赖自己的 `CastDateContext` 类型。
- 如果日期输入无效或时区不可用，应显示清楚的错误；不应回退到系统默认时区且不通知用户。
- 结果中保留 `conventionId`、库版本和“已确认/暂定/有分歧”状态，便于日后追查。
- 不要在每次渲染时多次重复计算；由纯函数计算并在输入变化时更新即可。

## 8. 决策准入条件

在将历法模块标记为完成前，必须满足：

- 已明确并记录年界、月界、日界和时区约定。
- 候选库 API 的用法来自官方 README/API 文档，而不是模型猜测。
- 固定版本、许可证和更新来源可查。
- 核心测试 fixture 有来源并全部通过。
- 至少与一个独立实现或可信万年历对关键日期进行交叉核对；重要边界至少双重验证。
- UI 单独显示年柱、月柱、日柱、月建、日辰，并提供清楚的时间/时区信息。
- 没有把仍存争议的口径伪装成确定答案。
