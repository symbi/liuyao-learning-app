# 课堂案例

本目录保存从课程中拆分出来的单个课堂案例。理论课和案例课都可以有独立案例；每一课使用自己的子目录：

```text
materials/class-cases/
├── README.md
├── lesson-05/
│   ├── case-001.json
│   └── case-002.json
├── lesson-14/
│   ├── case-001.json
│   └── ...
├── lesson-19/
│   ├── case-001.json
│   └── case-002.json
├── lesson-18/
│   ├── case-001.json
│   └── case-002.json
└── ...
```

每条案例的 JSON 与同目录配对的 `case-xxx-analysis.md` 表达的是同一份案例内容，只是形式不同：JSON 用于程序读取和结构化保存，MD 用于人类阅读。两者内容应保持一致，不能把 MD 当作可以额外增加分析内容的独立资料；文件内部仍须区分老师讲解、用户补充与 AI 推算等来源标注。如果将来确实需要独立的扩展分析文档，应另行单独定义，不混入本次 JSON/MD 配对设计。

每条案例记录至少需要：

- `recordType`: 程序识别，固定为 `class-case`
- `id`: 程序生成的案例 ID
- `category`: 在 HTML 里选择的 Category
- `tagOrRealQuestion`: 可选文字，写 tag 或当事人真正的问题
- `casting`: 可选卦盘快照，有可靠资料才保存
- `teacherAnalysis`: 根据课堂资料整理的老师分析摘要和结论；ASR 原文留在 Private raw，不整段复制

课次由所在文件夹 `lesson-XX` 确定，不需要再让用户重复填写。Category 不作为目录名，不需要建立分类子文件夹。

## 案例的文件形式与身份

同一个课堂案例在仓库中可能有多种文件形式，它们是同一个案例的不同来源与表示，不是多个案例：

- **案例 JSON**（本目录 `lesson-XX/case-xxx.json`）：结构化案例记录，有自己的稳定案例 `id`（如 `L19-C01-work-transfer`），通过 `dailyRecord.recordId` 显式关联 HTML 每日记录中的对应子记录。
- **课堂案例 MD**（同目录 `case-xxx-analysis.md`）：与案例 JSON 配对的同一案例的可读表示，表达与 JSON 相同的案例内容、仅形式不同，与 JSON 同属一个案例 `id`，不是独立案例，也不是额外的分析来源；文件内容中仍须区分老师讲解、用户补充与 AI 推算。它与下面每日记录的自动生成 MD 是两类不同的 MD。
- **HTML 每日记录**（`daily-records/` 下的每日 JSON 及其自动生成 MD）：每日 JSON 是容器，其中的子记录各有独立 UUID；自动生成 MD 是某个子记录的可读呈现（内嵌 `## 原始记录 JSON`），对应关系以子记录 ID 为准。生成 MD 不是独立案例，不得据此重复建立案例文件或重复计数；子记录的 `isCase` / `caseSource` 标记只用于分类，不能单独证明它已匹配到某个课堂案例。

课堂案例是老师在课程中讲解过的教学案例，不是用户的个人练习记录。整理时以案例 `id` 为身份中心，把课程笔记提及、ASR 讲解位置、HTML 记录和课堂案例 MD 表示都关联到同一个案例上。

## 和课程笔记、ASR 转录的对应

同一课的三份资料使用相同课次编号：

- Private raw 原始 ASR：`liuyao-learning-raw/lessons/lesson-XX/transcript-asr-raw.txt`
- Public Learning 该课总结：`docs/lessons/lesson-XX-notes-*.md`
- Public Learning 单独案例：本目录下的 `lesson-XX/case-*.json`

整理某一课时，按课次编号读取课程笔记、案例目录和 Private raw 原始资料，把案例对应到该课总结中，并添加案例链接。

### 案例来源优先级

1. **老师原始课堂资料优先**：有原始音频/视频/课件时，优先依据老师原始资料核对讲解；ASR 作为检索和定位辅助。
2. **没有原始音频时**：以现有 ASR 中能够辨认的老师讲解作为当前最重要的老师来源，但必须注明未经音频校正、可能存在识别错误；不能把 ASR 称为逐字原话。
3. **用户补充的卦盘**：用于还原案例盘面的卦宫、五行、上下卦、爻位、纳甲、六亲、世应、动爻和变爻；它是盘面来源，不替代老师的讲解来源。
4. **用户课堂 memo/重点笔记**：用于识别案例、理解背景和定位原始讲解。若与老师原始资料或可辨认的 ASR 讲解不一致，不得用 memo 覆盖老师说法。
5. **AI 计算和推理**：包括纳甲复算、伏神定位、五行关系及案例延伸解释，必须单独标为 AI/规则复算，不得写成老师原话。

若资料之间存在冲突，保留各来源的内容和差异，标注待核实点；只有在获得更可靠来源后才能校正，不要静默合并或把推断改写成事实。

课程笔记提到但没有足够资料独立复原的内容，可以继续作为该课的「案例线索」，不必强行建立完整案例文件。


## HTML 保存案例后的课程回查流程

用户今后会从 HTML 页面保存具体卦例。整理或分析这些记录时，不能只按 Category 猜课程，而应主动用卦盘信息回查课堂资料：

1. 读取案例 JSON 中的卦盘快照、问题、Category 和备注。
2. 优先按卦名、上下卦、世应、六亲、纳甲地支、动爻、变爻及日月信息，在对应课程笔记和案例目录中寻找候选。
3. 再回到 Private raw 原始录音/ASR，核对老师讲解的上下文和段落/时间戳。
4. 在案例记录中关联 `lessonId`、课程笔记路径、原始来源仓库/路径及可用的转录定位。
5. 只有卦盘和问事背景都能支持同一案例时才标记 `verified`；相似但不能确认的标记 `needs_review` 并说明理由；找不到就明确记为未找到。
6. 不得因卦象相似就强行对应；不得把 ASR 误识、AI 推断或用户后续个人分析写成老师原话。

匹配状态建议：
- `verified`：确认是课堂讲解的同一个案例，且来源位置已记录。
- `needs_review`：疑似匹配或关键信息不完整，等待原音/卦盘核对。
- `not_found`：现有课程资料未找到对应案例。
- `disputed`：不同来源之间存在需要保留的差异。
- 关于 `matched`：case-002 使用的历史值，与 `verified` 语义相同（案例身份已与课堂来源显式核对一致并记录依据），是同一状态的另一种写法，不是更低一级的状态。新案例统一使用 `verified`；工具读取旧文件时把 `matched` 归一化为 `verified`，同时保留原始值备查。注意：`verified` / `matched` 只表示案例身份已核对，不表示老师讲解已经过音频逐字验证；ASR 未校正、卦盘由用户提供等限定，仍以 `verificationBasis` 等字段为准。

案例链接关系建议保持为：HTML 案例 → 对应课程笔记 → Private raw 原始转录/录音位置 → 老师讲解摘要。课程笔记保留整堂课脉络，单个案例仍独立保存。
